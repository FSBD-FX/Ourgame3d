## SDK reasoning and alternatives

Installed UE5.5 [TextureCompiler.h](G:/UE_5.5/Engine/Source/Runtime/Engine/Public/TextureCompiler.h:46) declares FinishCompilation(TArrayView<UTexture* const>); TArray<UTexture*> matches the already compiled HUD Ready path. UTexture2D-to-UTexture is ordinary public inheritance conversion, and both include/call are WITH_EDITOR-gated. It runs on normal game-thread HUD BeginPlay, not inside PostCompilation routing. No API/casting blocker was found.

[Texture2D.cpp](G:/UE_5.5/Engine/Source/Runtime/Engine/Private/Texture2D.cpp:344) explicitly says size queries can return placeholder values while platform data is compiling and require FinishCompilation first. Its CreateResource registers incomplete textures and can produce a placeholder resource. [TextureCompiler.cpp](G:/UE_5.5/Engine/Source/Runtime/Engine/Private/TextureCompiler.cpp:379) waits requested pending jobs and invokes PostCompilation; that finishes platform cache and updates resources. Existing subsequent render Flush then drains resource commands. A plain prior render Flush does not finish these CPU compilation jobs. This directly supports the single async-compilation hypothesis, including possible wrong512 dimensions rather than only a null resource.

Frames is a UPROPERTY map of strong UObject references; declared full object paths and previously actually used16 textures show no static identity mismatch. A cached null entry would still be null and rejected: this patch does not manufacture or retry it. No runtime subpredicate evidence yet excludes that alternative, and no second fix or observer first-use LoadObject is recommended.
